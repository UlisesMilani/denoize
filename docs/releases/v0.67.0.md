## Highlights

- Added a loopback-only authenticated IPC server and client for trusted local
  automation. Capability documents scope planning, submission, status, history,
  pause, resume, cancellation, grant management, shutdown, canonical input and
  output roots, expiry, and queue priority.
- Added conservative dry-run admission, a bounded durable priority queue,
  one-at-a-time execution, lease recovery, verified checkpoints, atomic output
  publication, and signed-receipt reconciliation. Job state survives daemon
  restarts without guessing whether an output was published.
- Added desktop IPC job control while keeping bearer tokens and administrative
  grant operations outside the WebView. Eight stable discovery, capability,
  request, response, dry-run, status, and history schemas now ship in GitHub
  releases and the crates.io package.

## Compatibility

- IPC is opt-in. Existing file, batch, streaming, live-device, watch-folder,
  custom-model, checkpoint, receipt, and output contracts are unchanged. IPC v1
  binds only an ephemeral `127.0.0.1` TCP port and is not a remote service.
- The transport is length-prefixed JSON without encryption. Its security
  boundary is the local OS account plus owner-private discovery, state, lock,
  receipt, and bearer-capability files. Symlinks to regular inputs remain
  supported only when their canonical targets stay inside an authorized root.
- Because the denoize package version participates in the unchanged v3
  batch-resume recipe hash, v0.66 records are reported as `recipeChanged` after
  upgrading to v0.67. Existing outputs remain untouched unless `--force` is
  supplied. Regenerate once with `--force`; subsequent identical v0.67 runs
  skip normally.

## Safety boundary

- Every request, response, connection, timeout, queue, history, concurrency,
  memory, temporary-space, and GPU limit is finite. The server re-resolves job
  paths immediately before planning and execution, rejects path binding drift,
  and blocks processing flags that could escape its resource or publication
  policy.
- Batch and durable stream jobs pause only at verified checkpoint or atomic
  publication boundaries. File jobs have no safe mid-file checkpoint, so an
  uncertain child or daemon failure is reported and is never retried
  automatically. Cancellation preserves already published outputs and cannot
  emit a false success receipt.
- Revocation blocks future requests but does not silently delete admitted work;
  cancel queued or running jobs explicitly before revoking their capability.
  Terminal history is bounded and path-free, and receipt artifacts are pruned
  when their history entries age out.
