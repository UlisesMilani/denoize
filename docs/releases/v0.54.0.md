## Highlights

- Added network-free hardware discovery through `denoize hardware`, with
  human-readable, compact JSON, and pretty JSON output backed by the stable
  `denoize-hardware-v1` schema.
- Added explicit `cpu`, `auto`, `gpu`, `metal`, and `cuda` accelerator policies.
  Full builds can use Apple Metal or NVIDIA CUDA for the generic ONNX,
  MP-SENet, BSRNN, MossFormer2, SGMSE+, and GTCRN backends.
- Added the accelerator selector to the desktop app and propagated the exact
  requested/effective/fallback decision through CLI JSON, streaming results,
  reusable sessions, live processing, and batch recipe identity.
- Added the hardware schema to crates.io packages and GitHub release assets,
  including tagged-source asset verification before publication.

## Compatibility

- CPU remains the default. Existing commands retain their CPU behavior unless
  an accelerator is explicitly requested; `auto` prefers Metal, then CUDA, and
  reports an explicit CPU fallback when no compatible runtime is available.
- `gpu`, `metal`, and `cuda` are strict requests and fail before processing when
  the selected backend or host cannot satisfy them. Deterministic processing
  remains CPU-only and accepts only `cpu` or `auto`.
- File and streaming JSON results gain an additive `accelerator` object.
  Consumers of `denoize-cli-output-v1` must continue to ignore unknown fields
  added within the same schema version.
- `--max-memory` does not include GPU device memory or private allocations made
  inside third-party model runtimes. Use the CPU runtime when an externally
  enforced GPU-memory ceiling is required.
- Because the denoize package version participates in the unchanged v3
  batch-resume recipe hash, v0.53 records are reported as `recipeChanged` after
  upgrading to v0.54. Existing outputs remain untouched unless `--force` is
  supplied. Regenerate once with `--force` to migrate the saved recipes;
  subsequent identical v0.54 runs skip normally.
